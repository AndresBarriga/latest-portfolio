I used to write a PRD for a product I could only imagine. I handed it over and
found out weeks later whether the thing in my head matched the thing everyone
else pictured. Usually it was close. Close is expensive.

Now the first artefact is a working prototype I build myself in low-code. Not a
mockup. Something a customer can click through before anyone writes a line of
production code.

## A product that changed direction four times: TYNGO Spa

We planned digital check-in, advanced analytics, a configurable booking flow and
automated upselling. Almost none of it survived the first customer demos.

- **The configurable booking flow** looked like a selling point. Hotels saw
  twenty settings as homework. They wanted good defaults.
- **Upselling during booking** made a premium reservation feel like an online
  store.
- **Analytics** went unopened. Managers didn't have time for dashboards.
- **Digital check-in** removed the human moment reception wanted to keep. VIP
  guests needed manual handling by design, not by omission.

What we built instead came from watching what reception does all day: one
screen that runs the whole shift, scheduling that understands therapist, room
and equipment rather than only availability, treatment packages, and
cancellation recovery. One-click rebooking of the same treatment with the same
therapist in four weeks is not exciting. Reception uses it constantly.

All four rejected directions died in demos, before engineering committed. That

## What actually changed

**Validation moved before the build.** People are polite about descriptions and
specific about things they can use. So customer feedback arrives while changing
the product still costs an afternoon, and it is sharper, not only earlier.

**Handover became showing instead of explaining.** Developers use the prototype
before they read the PRD. The questions that come back are about edge cases, not
about what I meant.

**I catch my own bad ideas.** I used to evaluate an idea only once it was built,
which meant once it was already expensive. Now I often discard it before anyone
else has spent an hour on it.

**Design starts from something real.** UI/UX reviews a working flow instead of a
written description, and improves it rather than starting from a blank page.

<Callout>
**Build to learn, not to earn.**

The prototype answers three questions: is this valuable, will people use it this
way, and does it work as a business. Engineering builds the product that earns.
My job is to make sure it is worth building.

</Callout>

## The process

{/* diagram */}

**Discovery, which I own.** An idea becomes a clickable prototype, goes through
internal review, then in front of customers. The loop repeats until the idea
survives or dies. Only then do I write the PRD, so it describes something that
has already met the people who will use it.

**The handover call is where engineering commits.** We walk through the
prototype together. From there, being wrong costs weeks instead of an afternoon.

**Delivery, which engineering owns.** Developers write the TRD and
implementation plan, and an agent checks the TRD against the PRD to flag gaps
before anyone builds on an ambiguity. Work breaks into stories that agents
implement, reporting progress on the ticket. An agent reviews each change first;
a developer then reviews it and owns the merge.

**Validation doesn't stop at handover.** The build goes back in front of
customers before pilot, and again before production.

## It scales down

The full loop is for new products. Most work is smaller.

For a single feature or a change to an existing screen, the same sequence runs
in an afternoon: prototype the change, show it to whoever asked for it, adjust,
hand it over. The scale changes; the order doesn't. Something clickable exists
before anything is specified, and someone outside the team has reacted to it
before engineering commits.

This is now how the whole portfolio works, not an experiment on one product.

## What came out of it

**Fewer features nobody wanted.** Four rejected directions on Spa alone, all
caught before a sprint was spent on them.

**Features that get used without training.** What shipped came from watching the
work, so reception uses it daily rather than being taught to.

**Faster delivery, for a specific reason.** Duty Roster went from nothing to
production in under two months. Not because code was written faster, but because
nobody built the wrong version or reworked a misunderstanding.

## What I'm still unsure about

**The prototype is not the architecture.** It is a communication tool.
Engineering rebuilds properly from the PRD and TRD, and treating the prototype
as a foundation would be a mistake.

**Agent review changes what humans look at.** A developer still owns every
merge, but when an agent has already reviewed the diff, it is tempting to review
its findings instead of the code. That is faster, and I don't think anyone knows
yet what it costs. It is the question I would want answered before relying on
this any further.
