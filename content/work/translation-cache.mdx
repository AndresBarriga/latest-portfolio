Our guest-facing products render three kinds of content, and they have nothing
in common except that a guest reads all of them.

Static frontend strings are ours: they ship with the build and can be translated
ahead of time. Property configuration is the customer's: treatment names,
package descriptions, house rules. And live PMS data arrives at render time from
the system the hotel already runs.

Only the first can be translated ahead of time. The other two do not exist until
a customer configures them, and they change afterwards. That is why there was no
translation of dynamic content before this: not because nobody wanted it, but
because the obvious approach only covers the part the guest reads least.

## Translating at render time, once

So translation happens when the content is requested, and the result is stored.

Each cache entry holds the source text, the target language, the translation,
whether it came from the model or from cache, and a context field describing
what the string is for. That last field is the one that matters: the same word
in a button, a heading and a list of treatments should not always translate the
same way, and a model given only the word cannot know which it is looking at.
**The context field was in the design from the beginning, not added after we saw
bad output.**

The cache is shared across properties. If two hotels offer a treatment with the
same name, the second one is already translated. This is why the economics work
at all: **a string costs a model call once, not once per guest, and not once per
customer.** In a typical session almost everything is already cached; what is
left is content that changed since the last guest saw it, plus strings unique to
a property, terms and conditions being the usual case.

## The first render is slow, so we pay it in QA

The first render of uncached content is synchronous. The guest sees a spinner,
and a page that needs translating from scratch takes around five seconds. That
is not a good experience, and there is no version of on-demand translation where
it is.

What makes it acceptable is that a real guest almost never hits it. We warm the
cache in QA, per product, before a release, so the expensive path is walked in
our environment rather than at a front desk. **The penalty is real; the question
was only who pays it.**

## A fixed language list, not whatever the browser asks for

Languages are a fixed list, 30 today, rather than whatever a guest's browser
asks for. An open list multiplies cost and leaves nobody accountable for output
in languages we never chose to support. I set the list for the first product.
Newer products now choose their own, which is the right direction: the platform
should offer the capability and let product teams decide their market.

## Staff correct what the model can't know

The correction loop runs through staff. Anyone at the property can flag a
translation from the interface, and that entry gets corrected. This is
deliberate: the receptionist knows what the treatment is actually called. **They
have context the model does not**, and they are the ones who will hear about it
from a guest.
